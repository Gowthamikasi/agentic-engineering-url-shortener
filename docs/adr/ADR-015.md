# ADR-015: Authentication: a static API key with scopes

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-09-29 |
| Decision owner | Madhu |
| Reversibility | High |

## Context

How should write and control endpoints be protected in a prototype?

## Options considered

| Option | Assessment |
|---|---|
| No authentication | Simplest, and leaves the control plane open to anyone who can reach the port. |
| Static API key with scopes | Enough to separate read from write from control, and to attribute actions. |
| JWT with an identity provider | Realistic, and needs infrastructure this prototype does not have. |

## Decision

**An `X-Api-Key` header**, compared against SHA-256 hashes in configuration with `MessageDigest.isEqual`, carrying READ / WRITE / CONTROL scopes. The redirect endpoint stays public.

## Rationale

Scopes matter more than the mechanism here: a reviewer needs to be able to read a run without being able to approve its release gate. Keys are held only as hashes, every configured key is compared rather than short-circuiting on the first mismatch, and the key id - never the key - is what lands in the audit trail.

## Consequences

The recorded actor on a decision is asserted by the caller, not proven. That is the honest limit of an API key and is listed in the limitations; a real deployment needs an identity provider.
