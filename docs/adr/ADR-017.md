# ADR-017: Short-code alphabet: base58 for new codes, both accepted for lookup

| Field | Value |
|---|---|
| Status | Accepted - supersedes ADR-004 in part |
| Date | 2026-09-29 |
| Decision owner | Madhu |
| Reversibility | High - flip the configuration flag back. |

## Context

How can visually ambiguous glyphs be removed from new codes without breaking every existing link?

## Options considered

| Option | Assessment |
|---|---|
| Switch the alphabet everywhere | Clean, and instantly breaks every code containing 0, O, I or l. |
| Narrow minting, keep lookup wide | New codes are unambiguous; every code ever minted still resolves. |
| Migrate existing codes | Uniform afterwards, and it invalidates links already in the wild - which is the one thing a URL shortener must not do. |

## Decision

**Mint with base58; accept every known alphabet for lookup.** The alphabet is configuration (`urlshortener.short-code.alphabet`), and `ShortCodeValidator` accepts the union.

## Rationale

Migration was rejected outright: a short link that stops working is the worst failure this system has, and it would be invisible until a user hit it. Narrowing what is minted while keeping what is accepted wide is the asymmetry that makes the change safe. No data is mutated, so rollback is genuinely a flag flip rather than a restore.

## Consequences

Recorded during the brownfield scenario, which is where the impact analysis and its approval gate are exercised. The regression test that a legacy base62 code still resolves is the one that must pass both before and after the change.
