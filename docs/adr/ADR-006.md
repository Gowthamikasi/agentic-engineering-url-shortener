# ADR-006: Workflow state: append-only journal plus a derived snapshot

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-09-29 |
| Decision owner | Madhu |
| Reversibility | Medium |

## Context

How should run state be stored so a run can be reconstructed and resumed?

## Options considered

| Option | Assessment |
|---|---|
| Snapshot only | Cheap to read, but the history is gone: you cannot answer how a run reached its state. |
| Append-only event journal plus a derived snapshot | History is the source of truth; the snapshot is a projection. |
| In-memory only | Fastest, and loses everything on restart. |

## Decision

**An append-only transition journal** with a materialised snapshot derived from it.

## Rationale

Every question a reviewer or an operator asks - why did this node run twice, who approved this, what did the engine know when it decided - is a question about history. Storing only the current state answers none of them. `(run_id, seq)` is unique, which is also what stops a restarted scheduler appending a duplicate of an event it already wrote.

## Consequences

Reads for a large run cost more than a single row fetch, which is acceptable at this scale. The snapshot is held in memory and rebuilt from the journal; that rebuild path is the same one a resume uses.
