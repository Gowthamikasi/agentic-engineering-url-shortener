# ADR-005: Orchestration: a custom in-process DAG engine

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-09-29 |
| Decision owner | Madhu |
| Reversibility | Medium |

## Context

Should the control plane be built or adopted?

## Options considered

| Option | Assessment |
|---|---|
| Custom in-process DAG engine with a persisted journal | Full control over gates, replanning, classification and evidence. |
| Temporal / Durable Task | Production-grade durability and retries, but they own the execution model and hide precisely the behaviours being assessed behind their own abstractions. |
| A linear pipeline | Simplest, and explicitly called out in the assignment as insufficient evidence of orchestration. |

## Decision

**A custom in-process DAG engine** with an append-only transition journal.

## Rationale

The assessment is of the orchestration behaviour itself: how a gate blocks, how a failure is classified, how replanning preserves governance. A framework would answer those questions with its own semantics, and the interesting parts would become configuration rather than design. Building it also means the guarantees can be asserted - the state machine table is the governance model, and tests check it directly.

## Consequences

More code to own and to get right, and none of the durability guarantees a mature engine would bring. Mitigated by the journal being the source of truth and by the state machine refusing any transition not in its table.
