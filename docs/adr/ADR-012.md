# ADR-012: Observability: JSON logs, Micrometer metrics, and a first-class audit table

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-09-29 |
| Decision owner | Madhu |
| Reversibility | High |

## Context

What has to exist for a reviewer to reconstruct a run they did not watch?

## Options considered

| Option | Assessment |
|---|---|
| Console logs | Enough to debug, not enough to audit. |
| Structured logs plus metrics plus a dedicated audit table | Separates operational signal from the governance record. |
| A bespoke event store | More power, more to build and to explain. |

## Decision

**SLF4J/Logback JSON logs with run correlation in the MDC, Micrometer metrics on `/actuator/prometheus`, and an `audit_events` table with a per-run hash chain.**

## Rationale

Logs and audit rows answer different questions and degrade differently: logs rotate away and are allowed to, the governance record is not. Keeping the audit trail in its own table, behind a port that exposes only append and read, makes append-only a property of the type rather than of good intentions. The hash chain means a row cannot be edited out of the middle of a run without breaking every hash after it.

## Consequences

Tamper-evident, not tamper-proof: anyone with database access could recompute the whole chain. Detecting that needs an external anchor, which is out of scope and stated as such.
