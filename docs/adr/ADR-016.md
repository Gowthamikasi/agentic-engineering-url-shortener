# ADR-016: Analytics: an in-process bounded queue with a single writer

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-09-29 |
| Decision owner | Madhu |
| Reversibility | High |

## Context

How should clicks be recorded without slowing redirects?

## Options considered

| Option | Assessment |
|---|---|
| Write synchronously in the redirect path | Exact counts, and every redirect now waits on the database. |
| Bounded in-process queue drained by one writer | Redirects never block; counts are eventually consistent. |
| An external queue | Durable and scalable, and adds a runtime dependency. |

## Decision

**A bounded `LinkedBlockingQueue<ClickEvent>` drained in batches by a single virtual thread.**

## Rationale

Two consequences were chosen deliberately, not tolerated. Counts trail reality by up to about a second, which the stats response states in a `consistency` field rather than leaving the caller to guess. And under a flood the queue drops events - counted in a metric and exposed on the readiness probe - instead of applying back-pressure to redirects. Losing a count is the lesser harm compared with making every redirect wait.

## Consequences

A restart loses whatever is still queued. The readiness probe reports a saturated queue so the instance can shed traffic, which is a reason to stop sending it work but not a reason to restart it.
