# ADR-009: Failure handling: bounded retry for transient failures only

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-09-29 |
| Decision owner | Madhu |
| Reversibility | High |

## Context

When should the engine retry, and how many times?

## Options considered

| Option | Assessment |
|---|---|
| Retry everything | Maximises recovery, and repeats side effects and turns permanent failures into long hangs. |
| Bounded retry for transient failures only, then fallback or safe stop | Retries what can succeed, stops for what cannot. |
| Never retry | Predictable, and wastes genuine transient recovery. |

## Decision

**Bounded retry (default 3 attempts, exponential backoff with plus or minus 20% jitter) for `TRANSIENT` failures only.** Unknown causes are classified `PERMANENT`.

## Rationale

The default classification is the load-bearing decision. Misclassifying a transient fault as permanent costs one human decision; misclassifying a permanent one as transient burns the budget repeating something that cannot succeed and, for a node with side effects, repeats the side effect. So the engine fails safe, and an agent can escalate a failure to permanent but never talk the engine down to transient.

## Consequences

Retry lives in the engine, not in agents. An agent that retried internally would make the journal's attempt count a lie and hide a repeated side effect behind one apparent attempt.
