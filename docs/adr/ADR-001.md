# ADR-001: Application architecture: modular monolith with two planes

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-09-29 |
| Decision owner | Madhu |
| Reversibility | High - the module boundaries are where service boundaries would go. |

## Context

How should the prototype be structured so the boundaries being assessed are visible and enforced?

## Options considered

| Option | Assessment |
|---|---|
| Layered monolith | Simple, but the application and control concerns would share a package tree and the separation being assessed would be a claim rather than a fact. |
| Modular monolith with two plane assemblies | Real module boundaries enforced by the build, one process to run. |
| Microservices | Genuine isolation, at the cost of service discovery, transport, deployment and local-run complexity that the assignment explicitly warns against. |

## Decision

**Modular monolith**: separate Maven modules for the application plane and the control plane, both depending on `telemetry` and `contracts`, neither depending on the other.

## Rationale

The boundary is enforced twice - by the Maven module graph, which makes a violating import fail to compile, and by `ArchitectureBoundaryTest`, which fails the build if a dependency is added in either direction. A reviewer can verify the separation by running one test rather than by reading every file.

## Consequences

One process and one database file, so a clean clone runs with only a JDK. The cost is that the planes share a JVM and a datasource, so a runaway workflow could starve the shortener; that is documented as a limitation rather than solved.
