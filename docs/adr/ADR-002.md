# ADR-002: Language and framework: Java 21 with Spring Boot 3.3

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-09-29 |
| Decision owner | Madhu |
| Reversibility | Low |

## Context

What runtime gives the broadest coverage of the concerns being assessed with the least bespoke code?

## Options considered

| Option | Assessment |
|---|---|
| Java 21 + Spring Boot 3.3 | Mature answers for every assessed concern: OpenAPI generation, health probes, metrics, JPA, virtual threads for the scheduler. |
| Python + FastAPI | Faster to write, but weaker concurrency primitives for a scheduler and a less direct story for transactional persistence. |
| Node + Fastify | Fast to start, but the orchestration engine would need more hand-built machinery for bounded parallelism and timeouts. |

## Decision

**Java 21, Spring Boot 3.3, Maven multi-module.**

## Rationale

Virtual threads are what let the scheduler dispatch each node attempt on its own thread without a pool-sizing exercise; `Semaphore`-bounded parallelism then stays readable. Records give the domain and journal types value semantics for free, and pattern-matching switches make the state machine and recovery code direct.

## Consequences

Reversibility is low - this is effectively a rewrite decision. It is the one choice here that should get the most scrutiny before implementation.
