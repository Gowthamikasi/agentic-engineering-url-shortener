# ADR-007: Workflow definition: versioned JSON, validated as a DAG at load

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-09-29 |
| Decision owner | Madhu |
| Reversibility | High |

## Context

How should the graph be expressed?

## Options considered

| Option | Assessment |
|---|---|
| Hard-coded in Java | Type-safe, and invisible to anyone who will not read the engine. |
| Versioned JSON definition | Readable on its own, diffable, and versionable by replanning. |
| A code DSL | Expressive, but puts the governed path back inside the code. |

## Decision

**A versioned JSON `WorkflowDefinition`**, parsed with Jackson and validated as a DAG (Kahn's algorithm) at load.

## Rationale

A reviewer has to be able to see the governed path without reading the scheduler. Making the definition data also makes replanning honest: version N+1 is a diffable artifact rather than a hidden change in behaviour. Validation happens at load rather than at dispatch because a cycle found at runtime is indistinguishable from a stalled scheduler - the ready set simply stays empty and nothing explains why.

## Consequences

The definition becomes an input to protect: branch conditions are SpEL, so `BranchEvaluator` restricts evaluation to read-only property access, and agent types must be registered beans. A definition file cannot become a way to run arbitrary code.
